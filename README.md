# GuardDog —— 纯用户态防流氓软件防护工具

以 Windows 服务形态常驻，**先断根、后杀人**：发现黑名单进程时先挂起它，
清除它的全部自启动点与守护关系，再终止进程并处置源文件，
从而对抗流氓软件"杀了又起"的复活链。

- 纯用户态实现：不使用内核驱动 / 不做 SSDT、DKOM、内核 Hook
- 目标平台：Windows 10 / 11 x64
- 语言标准：C++17（MSVC / Visual Studio 2022）
- 构建系统：CMake 3.20+
- 零第三方依赖：JSON 解析、日志、匹配引擎均为自实现

> 使用须知：本工具会删除文件、覆写 PE 头、禁用并删除服务与计划任务。
> 所有危险操作在执行前都会校验目标是否命中黑名单（白名单优先级更高），
> 并先把原始值写入日志备份。请仅在自己拥有管理权限的设备上使用。

## 3. 构建

### 前置条件

- Visual Studio 2022，需勾选工作负载「使用 C++ 的桌面开发」（含 MSVC v143 + Windows SDK）
- CMake 3.20 或更高。若未安装，任选其一：
  - `winget install -e --id Kitware.CMake`
  - VS Installer → 修改 → 单个组件 → 搜索并勾选 **C++ CMake 工具**

### 构建命令

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

产物：`build/bin/GuardDogService.exe`

链接依赖：`bcrypt`（SHA-256）、`crypt32`（PKCS#7 / 证书）、`wintrust`（签名策略校验与 catalog）。

> 说明：程序编译为 **WIN32 子系统**（无窗口），入口点显式指定为 `wmainCRTStartup`，
> 因此既能用 `wmain` 接收宽字符命令行参数，又不会弹出控制台窗口。

## 5. 配置

### 5.1 位置与生成

- 运行时配置：`C:\ProgramData\GuardDog\config.json`
- 服务首次启动时若文件不存在，会自动生成一份默认配置（内容与 `config/config.default.json` 相同）
- 解析支持 UTF-8（含 BOM）；若文件被记事本存成了 ANSI(GBK)，会自动回退系统代码页重试

### 5.2 结构

```json
{
  "blacklist": [
    {
      "name": "规则名（日志里会显示）",
      "enabled": true,
      "process_names": ["流氓进程.exe", "推广*.exe"],
      "paths": ["C:\\Program Files\\流氓软件\\*"],
      "signers": ["某某公司"],
      "hashes": ["sha256:abcdef..."]
    }
  ],
  "whitelist": {
    "process_names": ["chrome.exe"],
    "paths": ["C:\\Windows\\System32\\*"],
    "signers": ["Microsoft Corporation"],
    "hashes": []
  },
  "settings": { "...": "见下表" }
}
```

### 5.3 匹配维度与判定顺序

黑名单规则内任一维度命中即视为命中该规则；规则之间是"或"关系。

| 维度 | 匹配方式 | 说明 |
| --- | --- | --- |
| `process_names` | 通配符 `*` `?`，大小写不敏感 | 与目标路径的文件名比较 |
| `paths` | 通配符全匹配，或目录前缀匹配 | `C:\Program Files\X` 命中 `C:\Program Files\X\a.exe`，但不命中 `C:\Program Files\XY\a.exe` |
| `signers` | 通配符，大小写不敏感 | 需文件签名通过 WinVerifyTrust 策略校验；支持**嵌入签名**与系统 **catalog（.cat）签名**两种来源 |
| `hashes` | 精确比较（已归一化） | 配置里写 `sha256:ABC`、`ABC`、带空格都能识别 |

**白名单优先级高于黑名单**：命中白名单的目标一律放行，即使它同时命中黑名单。
这是防误杀的硬性保障。

判定顺序（也决定了性能开销）：进程名 → 路径 → 签名者 → 哈希。
签名校验与文件哈希代价高昂，因此：

- 只有配置里确实存在某个维度的规则时，才会去计算该维度；
- 一旦便宜的维度已经命中，就不再做昂贵维度的计算；
- 计算结果按路径缓存（上限 4096 条，超出整体清空），避免兜底轮询反复读盘。

> 注意：`C:\Windows\System32\*` 这类系统目录被默认放在白名单里保护。
> 如果你确实要清理落在系统目录里的流氓文件，需要先从白名单中移除对应路径，
> 否则白名单会生效、黑名单规则不会被执行。

### 5.4 settings

| 字段 | 默认 | 含义 |
| --- | --- | --- |
| `poll_interval_ms` | 500 | 兜底轮询间隔（WMI 漏事件时靠它），会被夹取到 100–60000 |
| `wmi_enabled` | true | 是否启用 WMI 进程创建事件订阅（批次 3 使用） |
| `destroy_pe_header` | true | 删不掉时是否覆写 PE 头（批次 5 使用） |
| `delay_delete_on_reboot` | true | 是否登记重启后删除（批次 5 使用） |
| `observe_after_kill_seconds` | 300 | 处置后的复活观察期；设为 0 表示不观察 |
| `clean_wmi_subscriptions` | true | 是否清理 WMI 永久事件订阅（批次 4 使用） |
| `clean_legacy_on_start` | false | 服务启动时是否执行一次存量扫描（批次 5 使用） |
| `log_level` | info | debug / info / warn / error |

### 5.5 热重载

服务主循环每秒检查一次配置文件（修改时间或大小变化即触发重载），
**无需重启服务**，日志级别也会同步更新。

两条容错规则：

1. **重载失败保留旧配置**。编辑时漏一个逗号不会让正在运行的防护瞬间失效，
   日志会给出带行列号的错误定位（例如"第 1 行第 39 列：对象的键必须是双空格字符串"）。
2. **配置不可用时使用内置默认值**（黑名单为空）并明确告警，服务本身照常运行——
   服务活着才有机会继续监控与清理。

配置里没有任何启用的黑名单规则时，日志会打印
"当前没有启用的黑名单规则，防护处于观察状态"，避免误以为防护已生效。

## 6. 进程监控与处置

### 6.1 双路径发现

| 路径 | 机制 | 实测特征 |
| --- | --- | --- |
| 主：WMI 事件 | `Win32_ProcessStartTrace` 异步订阅，进程创建时回调 | 事件到达延迟约 **1–2 秒**（ETW → WMI 的传递开销所致，属机制本身特性） |
| 兜底：轮询 | `CreateToolhelp32Snapshot` 全量扫描，间隔由 `poll_interval_ms` 控制 | 默认 500ms；扫描约 300 个进程耗时约 140ms |

实测：从目标进程启动到被终止的总耗时 **67–645ms**，达标项来自轮询路径。
WMI 事件虽然延迟较高，但它不遍历进程、开销极低，且在 `poll_interval_ms` 配置得较大时
（例如 5000ms）是唯一的快速发现手段，因此仍保留为主监控路径。
两条路径投递到同一个处置队列，重复命中会被去重。

### 6.2 处置流程（批次 3 阶段）

```
WMI 事件 / 轮询命中
      ↓  轻量预筛（只比进程名与路径，避免无关进程挤占队列）
  处置队列（去重，上限 256）
      ↓
 二次校验：重新取路径 + 完整匹配（白名单优先）—— 危险操作只认"此刻的事实"
      ↓
 ① 挂起目标（NtSuspendProcess，一次冻结全部线程）
 ② 挂起后收集信息（路径 / 父进程 / 子进程）
 ③ 子进程一并挂起
 ④ （批次 4 在此插入自启动项断根）
 ⑤ 终止：TerminateProcess → 失败则降级 taskkill /F /T
 ⑥ （批次 5 在此插入文件删除 / PE 头破坏）
```

关键设计：

- **先挂起再动手**：被终止前的最后几毫秒足够流氓软件拉起守护进程或销毁证据。
- **终止失败必须恢复运行**：留一个被挂起的进程比留一个运行中的进程更糟
  （用户看到假死程序，且它持有的句柄会一直卡住资源）。
- **处置前二次校验**：从入队到执行之间 PID 可能已被回收，必须重新查路径、重新匹配。
- **子进程连带**：流氓软件常把真正的动作放在子进程里，只杀父进程等于没杀。

### 6.3 性能上的取舍

签名校验（WinVerifyTrust + catalog 查询）与文件哈希代价高昂，因此判定顺序被刻意排成：

1. 白名单的进程名 / 路径（纯字符串比较，最便宜）
2. 黑名单的进程名 / 路径
3. 只有黑名单里确实存在签名者/哈希规则时，才计算这两项
4. **只有目标已命中黑名单、即将被处置时**，才做白名单的签名者/哈希终检

第 4 步是防误杀的最后一道闸门：它让"白名单签名者规则"不再需要为每个无关进程预先算一遍签名。
在常见配置（只按进程名或路径拦截）下，无关进程完全不会触发签名校验——
这一改动把每轮进程扫描的耗时从秒级压到了百毫秒级。

## 7. 自启动项断根（核心对抗模块）

只终止进程是不够的：不清自启动项，目标下次开机（甚至几秒后被守护进程拉起）就会回来。
批次 4 因此实现了 8 类自启动位置的完整排查与清除。

### 7.1 覆盖的自启动位置

| # | 位置 | 实现要点 |
| --- | --- | --- |
| D1 | 注册表 Run / RunOnce | HKLM、WOW6432Node、HKCU，**以及 `HKEY_USERS` 下所有已加载的用户配置单元** |
| D2 | 启动文件夹 | 公共启动夹 + 各用户启动夹；对 `.lnk` 解析出真实目标再判断 |
| D3 | Windows 服务 | 先清恢复策略 → 停止 → 禁用 → 删除 |
| D4 | 计划任务 | 解析 `System32\Tasks` 下的 XML 取 `<Command>/<Arguments>`，用 schtasks 禁用并删除 |
| D5 | WMI 永久事件订阅 | 查 `root\subscription`，按 **绑定 → 消费者 → 过滤器** 顺序删除 |
| D6 | IFEO 映像劫持 | 检查 `Image File Execution Options\*\Debugger`，删除后清理空子键 |
| D7 | AppInit_DLLs | 按项切分列表，只移除命中的 DLL，保留其余注入项 |
| D8 | Winlogon | 检查 Shell / Userinit / Taskman，仅在确认被劫持时恢复默认值 |

几个容易踩坑、这里专门处理的地方：

- **HKCU 陷阱**：服务运行在 LocalSystem 下，`HKCU` 指向的是 SYSTEM 自己的配置单元，
  直接读它看不到登录用户的启动项。因此必须遍历 `HKEY_USERS\S-1-5-21-...`。
- **服务停不掉**：带恢复策略的服务被停止后会被 SCM 自动拉起。所以必须**先清恢复策略**；
  另外目标此时正处于挂起状态、无法响应优雅停止，超时后改为直接终止其进程。
- **服务删除是延迟的**：`DeleteService` 只打删除标记，注册表项要等句柄全关（常需重启）才消失。
  清理器会记录本次已处理的服务，避免"清除后复查"把它误报成残留。
- **WMI 订阅的删除顺序**：必须先删 `__FilterToConsumerBinding`，再删消费者与过滤器。
  反过来会留下指向已删除对象的悬空绑定，清理不彻底。
- **只删该删的**：所有判定都复用统一匹配引擎（含白名单优先），
  IFEO 只删 `Debugger` 值而不无脑删子键，AppInit 只摘掉命中的 DLL，
  Winlogon 只在确认被劫持时才恢复——避免破坏用户自己的正常配置。

### 7.2 清除与备份

- 每次清除前，被清除项的**原始值**都会以 `[BACKUP]` 标记写入日志，便于审计与人工恢复。
- 清理完成后自动**复查**（同一套 cleaner 切到只读模式再跑一遍），
  确认没有漏网；仍有残留时以 error 级别告警。
- 断根发生在**终止进程之前**：目标还活着时清自启动项，它的守护进程来不及补写新的；
  反过来先杀进程再清理，往往会被守护进程在中间空隙里重新注册。

### 7.3 守护进程的连带处置

"杀了又起"的典型结构是"守护进程 + 目标进程"。GuardDog 的处置顺序：

```
挂起目标 → 收集信息 → 挂起子进程 → 识别并挂起同目录的父进程（守护进程）
        → 断根（8 类自启动项）→ 终止全部相关进程
```

判定守护进程的依据是**父进程与目标位于同一目录**：同一软件的组件基本同目录部署，
而用户手动启动目标时父进程多为 explorer / cmd / pwsh 等系统程序，目录不同，不会被误伤。

## 8. 文件处置与存量扫描

### 8.1 文件处置：三级递进

| 级别 | 手段 | 说明 |
| --- | --- | --- |
| F1 | 直接删除 | 先清只读/隐藏/系统属性再删（流氓软件常靠属性逃避删除） |
| F2 | 解除占用后删除 | 用 Restart Manager 找出占用进程 → 挂起并终止 → 重试删除 |
| F3 | 重启删除 + 覆写 PE 头 | 登记 `PendingFileRenameOperations`，并把 PE 头前 1KB 清零 |

PE 头被清零后，Windows 加载器会报「不是有效的 Win32 应用程序」——
**即使文件还留在磁盘上，该程序也已永久报废**。这是对付"文件被驱动或守护进程长期占用、
怎么都删不掉"的最后手段。

处置顺序上，文件处置排在**终止进程之后**：文件被占用是删除失败的头号原因，
先让写它的进程消失，删除成功率会高得多。

### 8.2 安全边界

- `DestroyFile` 内部会**再次**校验黑名单（纵深防御），未命中直接拒绝并记 error。
  文件处置不可逆，"多校验一次"的成本远低于误删用户文件。
- 非 PE 文件不会被破坏头部：对数据文件做头部覆写没有意义，而且有害。
- 覆写前会通过 `IsPortableExecutable` 校验 MZ/PE 签名，避免误伤同名非可执行文件。

### 8.3 存量扫描（模块 E）

| 路径 | 做法 |
| --- | --- |
| E1 已安装程序 | 遍历三处 Uninstall 键，用卸载命令与安装目录内的可执行文件做匹配 |
| E2 运行中进程 | 复用轮询扫描器全量枚举，保持判定逻辑一致 |
| E3 安装目录 | Program Files / (x86) / LOCALAPPDATA / APPDATA / ProgramData 下一层目录内的 exe/dll/sys |

只扫一层、不递归：流氓软件的安装目录通常很浅，而深层递归既慢又容易误伤
（例如某个软件目录下嵌套着用户自己编译的测试程序）。

扫描本身**只发现不处置**，是否自动执行由 `clean_legacy_on_start` 控制（默认关闭）——
这类大范围动作应当由用户明确开启，而不是装上服务就自动发生。

## 9. 日志

- 目录：`C:\ProgramData\GuardDog\logs`
- 当前文件：`guarddog.log`（UTF-8 带 BOM，可直接用记事本查看）
- 跨天时自动归档为 `guarddog-YYYYMMDD.log`，超过 30 天的归档自动删除
- 格式：

```
2026-09-25 16:37:41.132 [INFO ] [T26064] 配置已加载：黑名单规则 1 条（启用 0）；白名单：进程 37 / 路径 11 / 签名者 2 / 哈希 0；轮询 500ms；WMI 启用；日志级别 info
```

字段依次为：本地时间（毫秒）、级别、线程号、消息。
级别取值 `debug / info / warn / error`，由配置文件的 `log_level` 控制。

危险操作（删除文件、覆写 PE 头、删除注册表项、禁用服务）执行前，
必须以 `[BACKUP]` 标记写入被清除项的原始值，便于事后审计与人工恢复。

## 11. 安全设计约定（后续批次遵循）

1. **白名单优先**：任何处置动作前先查白名单，命中白名单直接跳过。
2. **命中黑名单才动手**：删除 / 覆写 / 禁用前必须通过 `IsInBlacklist` 校验。
3. **先备份后动手**：注册表值、服务配置、任务 XML 等原始内容先进日志。
4. **先断根后杀人**：挂起 → 清自启动 → 终止 → 删文件/破坏 PE 头 → 持续观察 5 分钟。
5. **错误不跨模块抛异常**：统一用 `HRESULT` / Win32 错误码，失败必须写日志。
6. **签名不可只看自述**：任何签名者判定都必须先通过 WinVerifyTrust 策略校验，
   否则流氓软件只要在自己的证书里写个"某某公司"就能冒充大厂。
